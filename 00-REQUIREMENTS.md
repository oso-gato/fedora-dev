# Apparatus — REQUIREMENTS (spec of record: functional + non-functional)

> **THE WHAT** — what the apparatus must do: the numbered, testable requirements it must satisfy.

> **Confirmed by the maintainer.** Companion to [`00-OBJECTIVES.md`](./00-OBJECTIVES.md) (the WHY)
> and [`00-BUILDPRINCIPLE.md`](./00-BUILDPRINCIPLE.md) (how any artifact is constructed). This is the
> numbered, testable requirement set the apparatus builds to and the fitness gate grades against.
> **Numbers are never reused**, so the sequence has gaps where requirements were removed; every ID is
> cited by number across the codebase and must never be renumbered. Amendment is a new maintainer
> confirmation (R1), never a silent edit. Capabilities, not implementations.

## R1 — SINGLE-TOUCH INTAKE
An objective becomes a spec document whose numbered requirement set the maintainer confirms exactly once. The confirmed set is tamper-evident and immutable; fitness grades only the human-confirmed version; amendment is a new confirmation. (The dev-driven authoring of that document is R31.) **Immutability is ENFORCED, not merely asserted: a PR that modifies the confirmed spec — `00-OBJECTIVES.md`, `00-REQUIREMENTS.md`, `00-BUILDPRINCIPLE.md` — or the maintainer's constitution `00-GOVERNANCE.md` is MAINTAINER-MERGE-ONLY. The autonomous loop MUST NOT merge such a PR; it must reach the maintainer for an explicit merge. This is the one exception to the zero-gate auto-merge model, so amending the confirmed spec is a maintainer act by construction, never a silent or autonomous edit.** *(Acceptance: an otherwise-mergeable PR touching any of those four paths is not merged by the loop and is surfaced to the maintainer. The enforcement mechanism is the dev-owned `00-DESIGN.md`; the decision record is `00-GOVERNANCE.md` §6(f).)*

## R2 — AUTONOMOUS PLANNING
Confirmed spec → a numbered backlog of feature issues, one per feature, each closing only with proof links — the merged PR, the host GREEN verdict(s), and a **verified-live read-back** (the live artifact re-read and matched against merged source; merged ≠ live, so a deploy not confirmed live does not close the issue).

## R3 — AUTONOMOUS AUTHORING
Bounded judgment runs author each feature in a fresh, isolated worktree scoped to the session's declared repo-set; the first push opens a draft PR immediately. **No durable authoring/progress state persists outside GitHub — the loop is fully crash/kill/restart-resumable from the PR/issue stream — the sole exception being the per-session coordination namespace (lock, markers, scope, verdict-routing), local container state by design that constitutes the code-enforced isolation boundary.** The **mechanics of that isolated tree — per-session namespacing of all mutable local state and the branch re-verification before every commit/push — are the construction constraint [BP6](./00-BUILDPRINCIPLE.md), which governs every build and authoring action apparatus-wide, not just feature authoring; R3 requires authoring to happen inside it.**

## R4 — TIERED VALIDATION
**Scenario A (default):** Tier-1 in-box iteration to the nested engine's proven ceiling (build + assembly + lint), engaging the host **only for the live validation the container cannot perform itself** (at minimum the final pre-production shipment); on the host's RED verdict the session fixes and re-tickets **until GREEN**. **Scenario B (conditional fallback, not a choice):** entered only when the container cannot validate the build within itself at all (e.g. a systemd-PID-1 image that cannot boot in the nested engine), so Scenario A is unavailable; then every iteration round-trips the host against the draft PR's head sha from iteration zero.

## R5 — FIRST-CLASS TICKET BUS
GitHub issues/PRs are the sole IPC, WAL, and audit log. Typed tickets, line-1 machine grammar with a fixed verb allowlist and an explicit **per-session scope/routing token** on every ticket, claim, and terminal-outcome comment; an App/author-**authorization** check (App vs maintainer vs stranger) before parse — an authorization guard, **not** a session-isolation mechanism, since all sessions share one dev App identity. Full 40-hex sha binding on everything gating; verdict routing and idempotent claim/closure match on the **sha AND the session-scope key together**; a ticket whose scope key is undeclared/unreadable is consumed by nothing (fail-closed); the host echoes the originating session's scope key verbatim on its verdict. Claim comments for idempotent replay, terminal `outcome:` comments as closure, stale-ticket reopening. The sha-bound bus comment is the canonical verdict; check runs are its server-side mirror.

## R6 — INDEPENDENT SELF-CHECK
Every PR head sha is judged (a)(b)(c) by the **independent fitness identity** (`oso-gato-fitness-claudebox`, App id 4241099 — a non-author identity distinct from BOTH the authoring nox App and the host erebus App), grounded in the confirmed spec — never the PR's own body. Check (b) includes a mechanical red-line scan and fails any PR modifying its own `.live-gate` alongside product code (a PR may not carry both the product and the gate that passes it). Findings are generative: RETURN reasons feed the fixer.

## R7 — CLICK-FREE MERGE
Every PR in a repo **the apparatus operates on** (R16) merges with **NO human action** the instant both required independent gates — the **host live-gate** (posted by the erebus host identity) and the **independent fitness check** (posted by the distinct fitness identity) — are green for the head sha; both sha-bound, and the two gate identities MUST differ. No hand-merge by the authoring identity. **Server-side enforcement of these conditions is DELIBERATELY DECLINED** (00-GOVERNANCE §6(g)): making them required GitHub branch rules would move merge-gating out of code the apparatus can fix and into a setting only the maintainer can change — so a broken gate would become a human summons, conflicting with the single-interaction objective. The residual (a misused credential could merge without the gates) is accepted, recorded as **K2**, and bounded by automatic recoverability (git revert + health-gated rollback). **The one exception is the confirmed spec, which IS server-enforced** (R1) — because there, recovery is not automatic.

## R9 — REVOCATION (the hard stop)
Because all tenant sessions share one dev App identity, the **hard stop is revocation of that single shared key**, which necessarily stops all tenant sessions at once — there is no per-tenant hard stop via identity (isolation is by scope, code-enforced). Revocation is the stop of record: it needs no cooperation from the running loop and works when GitHub is unreachable. Push protection + org-wide secret scanning protect the shared credential; a leak triggers the kernel rotation runbook. Stopping the containers on the host is an equivalent local hard stop.

## R10 — AUTONOMOUS DEPLOY WITH RECOVERY BEFORE POWER
Post-merge: CI publishes; the host deploys the digest and confirms success by **reading the live deployed artifact back and verifying it matches the merged-source digest** (fail-closed: not done until verified live on the target) — a liveness/health probe being only one component of the read-back; on any read-back failure (unhealthy probe OR live-digest ≠ merged source) it auto-rolls back to the retained last-known-good digest and files a regression ticket. Autonomous deploys arm only after a rollback drill has demonstrably fired GREEN.

## R12 — RED LINE
Builds of non-apparatus/workload work structurally cannot mutate the host, fedora-dev, or fedora-bootstrap: throwaway trees on both boxes, no repo-mutating host verbs, pull-only deploys from CI digests, plus the fitness (b) scan. Building the apparatus itself is the sanctioned exception, expressed as spec requirements through the same gates.

## R13 — BOUNDED AUTONOMY
Every judgment run has a timeout, a no-progress stop (same failure signature + unchanged head sha), a **heartbeat** (a positive liveness signal whose absence is treated as a failure to surface, not evidence of progress), and a BLOCKED surfacing path (a dev-task question, never an approval request). Zero permission prompts; a prompt is a defect.

## R14 — END-TO-END PROOF
Acceptance = **E2E-A** (clean Scenario-A objective in a virgin repo), **E2E-B** (systemd-PID-1, every iteration host-run), **E2E-KILL** (both boxes killed mid-work, resume from the bus alone), **E2E-ISO** (≥2 concurrent sessions on disjoint declared scopes: each verdict routed only to its originating session, no session reads/acts on another's ticket, zero cross-session worktree/lock/marker collision, an undeclared-scope session fails closed to zero action — each objective shipping with human-interaction-count = 1), and **E2E-SELF** (an apparatus-scoped change merges and the pair staggers its own refresh — host rebuilds/restores the dev container from outside, dev instructs the host's agent to refresh the host — passing only when the live artifact read back matches merged source, fail-closed); each with fault injection (one injected RED recovered, one broken deploy auto-rolled-back). Pass = **human interaction count = 1** (spec confirmation), audited from the event stream. Commissioning + monthly canary. **R14 depends on R40:** an acceptance run cannot demonstrate an autonomous *close* before the loop can close an objective itself, so E2E-A/B and E2E-SELF are **sequenced behind the ship actuator — not waived**.

## R15 — CONFIG AS CODE (defense-in-depth)
A supporting **defense-in-depth** control on the merge-and-deploy boundary (revisit post-MVP). The branch-protection ruleset enforcing require-PR on `main` (and, if used, the App permission/gate-identity config) is mirrored as versioned in-repo JSON; **CODEOWNERS is load-bearing for the R1 confirmed-spec exception only** (it carries the maintainer-merge review-request on the four spec paths); it remains optional everywhere else, where zero-gate + code-enforced isolation govern. A scheduled audit compares live platform config to the mirror and, on drift, files a regression ticket onto the bus for the owning apparatus session to self-correct.

## R16 — OPERATING SCOPE (the App installation)
The apparatus operates on **every repository its GitHub App is installed on — whatever the maintainer installs it on, private repositories included** — **enumerated live by the apparatus from its own installation** (`bin/repo-scope.sh`), never a hardcoded list, a config file, or any software allowlist. **There is NO enrollment allowlist, NO confirm-to-add ceremony, and NO fixed 'forbidden' set:** a GitHub App cannot create a repository on a personal account, so every repo is human-created, and the maintainer's **repo-creation + App-install** IS the authorization (a non-coding act); removing the App de-authorizes. **Scope is the maintainer's per-repo choice and the apparatus MUST NOT widen it** — a request to reach a repo outside the installation is surfaced to the maintainer, never self-provisioned around. **Per-session scope is multi-tenant COORDINATION ONLY** (which in-scope repos a live session is actively working, for disjointness R28 and verdict routing R5) — **NOT as an authorization ceiling**. **Fail-closed** to the apparatus's own two repos `{fedora-dev, fedora-bootstrap}` when the installation is unreadable, so the loop can always fix and ship itself.

## R17 — REBUILD CONTINUITY
A purposeful rebuild is a complete lifecycle: **KILL** all processes/sessions (by construction, no ghost) → **REBUILD** to the new spec → **RESTORE** every prior session on the new container → **RESUME** (kick-started and actively working, not merely present) → **VERIFIED — fail-closed, not done until proven live on the target: (1) the live dev container's running image/spec is read back and matches the newly-merged dev-container repo source, AND (2) every restored session is alive AND active, container identified by ID never name**; the routine tick still defers to session-lock. Orchestrated by the **pair**: the host executes the dev-container KILL/REBUILD/RESTORE from outside via the ticket bus + podman (neither box rebuilds itself). Depends on liveness-bound locks (R26).

## R18 — LIVENESS / STALL DETECTION
Monitor for the **ABSENCE** of progress, not just presence: every long-running component and orchestration has a deadman that fires when expected progress does not occur within a bound; a per-stage progress fingerprint; **IDLE-WITH-WORK-PENDING** is a first-class alarm; a completion is an announced event; quiet when healthy. Additionally each long-running process **emits a periodic heartbeat that an independent/supervising context reads, so liveness is observed positively, not merely inferred from the deadman staying silent; the watchdog decides liveness from the real heartbeat, never from a proxy (log mtime, worktree write, a lock's existence); absence of a heartbeat OR of an expected completion signal past its bound is surfaced as a failure, never read as progress.** Coverage spans the poller, supervisor, host watcher, host live-gate build, dev-author/fixer, and refresh orchestrations. The watchdog is not defeatable by the process-pattern self-match bugs it hunts (probe binaries/PIDs, never strings).

## R20 — MULTI-SESSION ISOLATION
N isolated claudebox sessions per dev container, each bound to its own declared **disjoint** repo-set; one shared host validator over the union of all sessions' repos; **session-exclusive ticket pickup** — a session acts on and even reads only its own session's tickets, never another's. Isolation is by per-session state namespacing (lock, markers, scope, verdict-routing) — a **code-enforced boundary (not identity-enforced) under a single shared dev App identity, fail-closed to nothing if a session's scope is undeclared.** Session-aware control: **dev-container refresh/rebuild is a whole-container operation** on the single shared dev container — it rebuilds all resident sessions together; there is no per-session `rebuild-devbox`.

## R23 — RECIPROCAL PAIR SELF-REFRESH (HOST DIRECTION)
Merged is not live, in **both** directions. When a change to the **host/bootstrap repo** merges, the **dev container drives the host** to that merged development by filing a host-refresh ticket instructing the host's agent over the bus — the dev box never touches the host directly, the reciprocal of R17's host-driven dev-container rebuild (neither box rebuilds the very agent doing the work). A merge to **either** apparatus repo **automatically arms** the matching refresh with no human step; the ordering is staggered/pair-driven. Every refresh, host and dev-container alike, is confirmed by reading the live artifact back against merged source and is fail-closed — on failure it rolls back and re-tickets.

## R24 — STANDING EMPIRICAL-PROOF / NO-PROXY RULE
No gating outcome anywhere — live-gate verdict, fitness pass, deploy/health confirmation, refresh confirmation, config-drift audit, planning-close proof, or liveness decision — is accepted on an agent's assertion, from memory, or against a baseline that has shifted under development. Each is proven **at check-time by reading the REAL live artifact** bound to the exact state judged (the running container's live image digest, the actual process/PID, the real file/config on target, the merged source), **cross-checked by a non-author context** where it gates a merge or deploy, and **never satisfied by a proxy** — clone-HEAD for running-HEAD, a lock's existence for a live holder, a CI/build log for the deployed digest, a merge event for a live deployment, "looks green" for the artifact read. A known-proxy substitution is a reviewable defect; an outcome asserted-but-not-read is treated as a failure to surface, not a success.

## R25 — VERDICT BASE-DRIFT VOIDING
Every gating verdict (live-gate GREEN/RED, fitness PASS) is bound to **BOTH the head sha AND the merge-base (target `main`) sha** it was computed against, and is **automatically void once the base branch advances past that merge-base** — the verdict must be recomputed against the current base before it can gate a merge. A judgment issued against a since-shifted baseline is never honored; a PR rendered unmergeable by base drift is routed to the fixer rather than left to spin. Acceptance: GREEN on head H over base B, advance `main` past B, assert the merge does not proceed on the stale verdict and re-validation is required.

## R26 — LIVENESS-BOUND LOCKS & MARKERS
Any lock, marker, or claim that gates whether work proceeds is **liveness-bound**: a lock held by a dead or absent holder is detected and reclaimed, and a lock's mere existence is **never** accepted as proof its holder is alive. A stale lock must not silently turn a restart/restore/sweep into an `rc=0` no-op; holder identity is verified against a **live PID/heartbeat (no proxy)**, and a would-be no-op caused by a stale lock surfaces as a fault. Acceptance: leave a stale lock from a killed holder, start a new instance, assert it detects the dead holder, reclaims the lock, proceeds, and never silently no-ops.

## R27 — SESSION REGISTRY
The apparatus maintains a **durable, versioned SESSION REGISTRY** — the single source of truth enumerating each declared session (**session-id, declared scope/repo-set, container id**) — persisted on the home volume so it survives box recreation. Every session-aware actuator (rebuild/restore, verdict routing, scope-disjointness check) reads the registry. **Each entry's repo-set records which in-scope repos that session is ACTIVELY WORKING — COORDINATION for disjointness (R28) and verdict routing (R5), NOT authorization** (authorization is the App installation, R16). The registry is **seeded by binding each live session to the repos it is working** and maintained across rebuilds (R17 restores from it). Acceptance: kill and rebuild the container, then assert every registry-listed session is restored and resumed, each identified by container id (never name); and assert two sessions cannot both hold the same repo (R28).

## R28 — SCOPE DISJOINTNESS ENFORCEMENT
Session scopes across the dev container are **pairwise disjoint**. Before acting on any repo a session verifies (against the R27 registry) that no other declared session's scope contains that repo; an overlap (two sessions claiming the same repo) is a detected fault that **fail-closes BOTH claimants off the contested repo** and surfaces a BLOCKED question — never a first-come race, double-author, or double-merge. Acceptance: declare two sessions whose scopes intersect on repo X; assert neither authors, validates, or merges any PR in X and the overlap is surfaced.

## R29 — CONCURRENT SHARED-VALIDATOR SAFETY
The single shared host validator processes concurrent tickets from multiple sessions **without cross-contamination**: each validation runs in its own throwaway tree/candidate keyed by **BOTH ticket sha AND session-id** (no shared build state between two sessions' candidates), the shared package cache and orphan sweeper are **concurrency-safe**, and scheduling is **fair** so no session can starve another's tickets indefinitely. Acceptance: two sessions file live-validate tickets simultaneously; assert both receive correct GREEN/RED verdicts routed to the right session and neither build reads or clobbers the other's tree.

## R30 — WHOLE-OBJECTIVE COMPLETION RECOGNITION
The run recognizes **whole-objective completion structurally**: the spec/objective closes only when **every feature issue in its R2 backlog is closed with its proof links AND the aggregate product is verified shipped end-to-end (live/deployed)**, with **no human sign-off** on the final shipment. Until that condition holds the loop keeps iterating; when it holds the objective is marked shipped autonomously and the run ends.

## R31 — REQUIREMENTS ELABORATION / DEV-DRIVEN INTAKE
Intake is **dev-driven within the single R1 interaction**. On the maintainer's raw objective the dev container **authors a tightened AND expanded objective set plus a derived numbered functional-requirement set**, and settles it through discussion, **before** the one confirmation. The confirmed, tamper-evident, immutable document records **BOTH the objective and the functional requirements**, and it — not a transcription of the maintainer's words — **becomes the build objective**. The whole exchange (objective stated → discussion → single confirmation) counts as **exactly one human interaction** for R14's audit, after which the run is autonomous to ship.

## R33 — THREE DECOUPLED REBUILD CLOCKS + CLAUDE-CODE SELF-CADENCE
The platform maintains **three independent rebuild cadences — host image, dev-container image, and the claudebox-resident Claude Code — each advanceable without forcing the other two**. Because Claude Code advances daily and is containerised, claudebox carries its **own update actuator** that refreshes it to the latest official-channel release on **its own clock**, decoupled from dev-container recreation (R17) and host refresh (R23), admitted per the [BP1](./00-BUILDPRINCIPLE.md) provenance hierarchy and **verified by reading the live installed version back** (no proxy). None of the three clocks forces a rebuild of the others; each is separately triggerable and separately verified.

## R34 — SPEC-VS-BUILD SHIP GATE
A product is declared ready and **shipped only after** the build is complete, **validated at the right tier (R4)**, and has **passed an independent SPEC-VS-BUILD review**: a separate agent-context — **adversarial and critical**, with **architecture-aware reviewers applying the [build principles](./00-BUILDPRINCIPLE.md)** — that verifies the **built product** conforms, in order, to (1) the **objective**, (2) the **functional and non-functional requirements**, and (3) the **build principles**. **The design (`00-DESIGN.md`) is NOT a conformance target** — it is the dev's own mutable means, not the confirmed spec. The author is **never its own sole judge** (this is distinct from and additional to the per-PR fitness check R6: R6 grades each change; R34 is the whole-product gate at ship). **Outcome:** PASS → the product may ship (the R30 whole-objective completion recognition then closes the objective, no human sign-off); **not-PASS → the product is sent back and the loop continues** (develop → validate → review) until it passes. Acceptance: a built product that violates a requirement or a build principle is caught by an independent review and returned, and the objective does not close until a spec-vs-build review PASSES against the shipped aggregate.

## R35 — DEPLOY-INTERFACE CONTRACT
Every **deployable image artifact exposes exactly ONE sanctioned, non-interactive run path** that declares its **complete runtime shape — health command, devices, volumes, restart policy, and port set** — and is the **single source of runtime truth** for that artifact; an interactive spin-up wizard may only **delegate** to it (never a second source of truth), and the systemd-managed **Quadlet is its managed equivalent**. **Bypassing that path to hand-roll the container-engine run is disallowed.** Network exposure of the declared shape follows **R36** (sensitive ports tailnet-only, never publicly published); the **deploy and self-refresh behaviors of R10/R23 CONSUME this interface** — they read the live artifact back *through* it — rather than restating it. The **host-as-platform is the disclosed categorical carve-out** (it is brought up by `setup.sh` genesis, not deployed as a workload image, and ships no such run path). Per-repo `CLAUDE.md` **Principle 7 is the concrete per-artifact instantiation** of this contract (the real `run.sh`/`spin-up.sh`/Quadlet with its actual device/volume/port set); this requirement is the authoritative apparatus-level statement it instantiates. Fitness treats a deployable image lacking a single sanctioned run path, a second competing source of runtime truth, or a publicly-published sensitive port as a blocking finding.

# NON-FUNCTIONAL REQUIREMENTS

> **Qualities the running apparatus must have** (as distinct from the functional requirements above —
> what it must *do* — and the build principles, how any artifact is *made*). Graded by the same
> fitness gate. Numbered in the same R-sequence — a requirement is a requirement.

## R36 — RUNTIME SECURITY POSTURE
The apparatus runs at **least privilege, minimal exposure, and install-bounded scope**: components run with the **narrowest privilege** their function needs (the rootless-user-namespace posture, no needless capability or host reach); **network exposure is minimized** (sensitive ports tailnet-only, never publicly published; loopback-only validation fences); the **three App identities reach EXACTLY the repositories the maintainer has installed them on** — this App-install boundary IS the operating scope (R16) and the credential-level wall between the two camps: **what is in scope is the maintainer's live install choice, private repositories included; the apparatus must NEVER itself install, request or otherwise WIDEN its own installation** — self-widening scope is **(b) UNSAFE**; and **no credential or identity is ever baked into a built layer** (secrets enter only as runtime inputs, and the entrypoint fails fast when a required one is missing). A change that broadens privilege, publishes a sensitive port, **self-widens the App installation**, or lands a secret in a layer is **(b) UNSAFE**.

## R37 — NO SILENT CAP / NO SILENT DEGRADATION
**Any actuator that caps, drops, defers, truncates, self-disables, or otherwise does less than its full job MUST emit a signal** — a log line, a surfaced question, a stamped verdict — and a **would-be no-op surfaces as a fault, never as silent success.** This generalizes the lock-liveness rule (R26, locks) and the process-liveness rule (R18, stalled processes) to the whole class of **"alive but silently not doing its job"**: a truncated diff handed to a reviewer, a capped backlog, a self-refresh that silently self-disabled, a flock corpse read as a healthy peer. It is the running-system counterpart of the objective's "distrust your own reports": the system must not let a bounded/degraded path masquerade as a complete one. A cap/drop/defer/self-disable with no signal is a reviewable defect.

## R38 — UNIVERSAL RECOVERABILITY
**Every autonomous mutation the apparatus makes is reversible** — not only deploy (R10's digest rollback), but **merge (git revert), issue/PR closure (reopen), scope change (re-declare/narrow), and rebuild (restore from the registry)** — so the zero-human-shipment model always retains an automatic path back to the last-known-good state. The fitness gate's standing **preserve-recoverability** rule (a change that removes a rollback path, or exfiltrates the merge/secret credential, FAILS) enforces this at review time. **DRILL HARNESS:** `bin/recoverability-drill.sh` PERFORMS each reverse operation against a DISPOSABLE fixture and fires GREEN only if it restores the pre-mutation state, exposing a `guard <mutation>` ARM GATE (rc 0 iff the drill fired GREEN). **merge (`git revert`)** and **scope (`transcribe-narrow`)** are drill-proven OFFLINE; **rebuild (`restore-from-registry`)** is drill-proven with the container engine; **close (`reopen`)** is STAGED — the reverse is a live GitHub verb, disclosed (R37), never faked. The per-actuator arm-WIRING (each actuator calling `guard` before it arms) is not yet built; until an actuator is wired, recoverability for it is review-enforced rather than drill-gated.

# AUTONOMY-PRESERVATION REQUIREMENTS

> **Requirements that keep the loop running.** A gate specified fail-closed is correct in isolation, but
> a closed gate with no self-heal is a **human summons**. These requirements hold the balance the
> objective demands: *distrust yourself* AND *need no human*. Graded by the same fitness gate.

## R39 — GATE RESILIENCE *(the keystone)*
Every gate that can block the loop has a **bounded, automatic recovery path**. A gate that is unavailable, stalled, or erroring **MUST NOT block indefinitely**: it retries, fails over to a defined alternative, or degrades under a **recorded** policy (R37 — never silently), and surfaces to the maintainer **only after bounded attempts have failed**. **A gate's own failure must never require a human merge to clear.** Acceptance: disable each blocking gate in turn (host live-gate, fitness, publish, deploy read-back); the loop recovers or escalates within its stated bound, and no PR requires a human merge to land.

## R40 — AUTONOMOUS SHIP ACTUATOR
The loop **itself** invokes the ship gate (R34) and closes the objective (R30) once the backlog is empty and the acceptance evidence exists. **No human notices completion or triggers the close** — the recognizer is not enough; the actuator is required, because an objective that only a human can declare finished is not an autonomous run. Acceptance: with an empty backlog and a conformant aggregate, the objective transitions to shipped with zero human action.

## R41 — DEPLOY-TO-LIVE AUTONOMY
The merged→live path carries **NO standing human tap**. A merged change reaches the running target automatically — health-gated, with live read-back verification and automatic rollback on failure (R10/R23) — including changes that require a container recreate. **Human approval governs GOALS (R1), never deployments**: a deployment is reversible by construction, so gating it buys nothing and costs autonomy. Acceptance: merge a change to any deployed artifact, including one requiring a recreate, and it becomes live and verified with no label, click, or comment from the maintainer.

## R42 — CONTINUOUS AUTONOMY ACCOUNTING
The loop **continuously measures and publishes its own human-interaction count** — every merge, label, comment, or settings act a human performs on its work — not only at acceptance (R14). Drift toward human involvement is visible **within the cycle it occurs**, not at an audit months later. Acceptance: a human merge or label on any in-scope PR appears in the published count within one reporting cycle.

## R43 — GATE BUDGET DISCIPLINE
**No new blocking gate may be added without a proven self-heal path (R39).** A change that introduces a gate able to stop the loop, without a bounded automatic recovery, is **(b) UNSAFE** at review. This is the structural rule that prevents the drift from recurring: detection may only be added together with recovery. Acceptance: the fitness gate RETURNs a PR that adds a blocking gate carrying no recovery path.
